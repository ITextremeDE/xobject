# ADR 0024: Primary levels and relationship endpoint conditions

- Status: Accepted for the local implementation
- Date: 2026-11-03
- Extends: [ADR 0019](0019-record-relationships.md), [ADR 0021](0021-relationship-scope-and-projects-module.md) and [ADR 0023](0023-record-journal-and-conditional-fields.md)

## Decision

The Projects & Tasks module supplies fixed Contact → Project → Case levels. Activation creates protected base Contacts, Projects, Cases and Tasks with standard fields and binds their UUIDs atomically. The levels are not user-configurable; there is no `configure_primary_chain` API/MCP operation. Module activation uses the schema barrier, common Administrator/Designer authorization, optimistic module version, graph preflight and atomic per-field journals. `sys_primary_chain_levels` retains the UUID role mapping; `sys_module_object_bindings` identifies supplied definitions independently of display or technical names. A matching custom name causes activation to fail without adoption or partial changes. Full domain templates remain later work.

Primary is available for all child object types while Projects & Tasks is enabled. Contact is a root, a Project may belong to a Contact, a Case may belong to a Contact or Project, and any other object may belong to one of these levels. Levels in individual record paths may be absent. Direct-parent uniqueness and cycle checks remain authoritative. Candidate filtering applies fixed role rules before counts/pagination; all writes use the same rule. Disabling the module requires removing existing Primary links, retains definitions/records/bindings and removes Primary fields/context. Re-enabling reuses the same UUIDs. Bound objects remain protected against deactivation/deletion.

Record Details shows the available levels as a single chain of single-value InputGroups. Earlier levels are inherited and read-only; only the direct relationship is persisted. A level-specific selection dialog can replace the direct association with a more specific level. To move to an earlier direct level, clear the current direct association first. `get_primary_chain_context` resolves persisted or proposed direct parents through the shared content authorization and real graph. It does not write journals or copy ancestor values. Explicit custom relationships use one table per applicable definition under ADR 0019. General links are edited from the record-header action; General links and subordinate Primary records are listed in the Dossier.

Custom relationship definitions may constrain each endpoint using the same unconditional single-choice controller/option identities as field applicability. Conditions belong to the corresponding object pair; symmetric endpoints require equivalent conditions. The common API/MCP validates definitions, preflights existing edges and filters candidates before pagination. Final record writes validate retained edges even when only a discriminator field changes. Incompatible links must be explicitly removed; values and connections are never silently cleared. Controller fields/options cannot be removed or converted incompatibly while referenced.

The definition editor reuses one applicability component for fields and relationship endpoints, with unique control IDs. The Contact fixture configures Organization → Contact person with a maximum of one Organization per Contact person. Identities is a symmetric multiple relationship among Contact persons and Individual contacts. It is a direct list on Contacts, with no Identity object type and no inferred transitive grouping. These are regular configured rules, not runtime branches based on object names. Full Contacts module templates, supplied-definition ownership, derived Keywords and dependent company/name requirements remain separate work.

## Migration and identity handling

Migration 4 introduced additive role storage. Migration 7 adds the database-backed module catalog and freezes previously explicit UUID roles as module bindings, without name-based adoption. Preserve business rows, edges, authentication and original history; verify a backup before applying upgrades. Keep the original numbered migration behavior independent of newer read projections. Normal operator/runtime-role separation applies to the new table. Shared UUID schemas canonicalize identity spelling at channel boundaries, keeping technical/display names and arbitrary content separate.

## Verification

Integration tests cover API/MCP context parity, inherited and skipped levels, identity spelling, candidate restrictions, stale module versions, fixed level identities, activation conflicts, preflight rollback, object lifecycle and content access. Endpoint tests cover conditional candidates, incompatible target rejection, scalar-change rollback, controller protection and symmetric Identities links. Browser acceptance covers derived drafts, Reset, correct Contact-kind visibility, selection restrictions, configuration guards, keyboard interaction and narrow layouts. Local development migration retains the existing business records, edges and original content journals; no publication or release is implied.
