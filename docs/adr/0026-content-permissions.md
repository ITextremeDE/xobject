# ADR 0026: Object, field and record content permissions

- Status: Accepted for the existing local ACL; expanded product target specified in PRD section 4
- Date: 2026-11-03

## Product-model revision — 2026-11-04

The agreed [PRD permission concept](../PRD.md#4-permissions) replaces this ADR's product target with graded ownership, foreign access, membership inheritance and expanded rights. The four-level ACL described below remains the current local implementation; it is not evidence that the new model is delivered. Preserve its data and safeguards until a follow-up implementation ADR and access-preserving migration are accepted. Calendar and notification capabilities remain later work.

## Existing implementation decision

Workspace membership and the Designer role govern configuration; they never imply content access. Installation-wide Administrators retain full content access, including records outside their own memberships. They remain subject to validation, immutable journals, protected definitions and lifecycle confirmation. Only Administrators configure content grants and object sensitivity. The own-account security boundary is unchanged.

Migration 8 adds `sys_content_grants`, `sys_object_types.is_sensitive` and an independent optimistic `permissions_version`. Grants are keyed by object UUID and a workspace user/group identity. Object levels are None, Read, Edit, Delete and Full access. Edit includes creation. Delete and Full access define the authorization levels for the separate future recycle-bin/permanent-deletion operations; this change does not implement those lifecycle operations. Full access permits changing Access principals but does not override field restrictions.

Group object levels add by taking the highest grant. An explicit non-null user object level replaces that result. Field levels are None, Read and Edit; Edit includes Read. An explicit user field level replaces the corresponding group result. Otherwise each active group contributes its field exception or its object-level field default, and the highest wins. If no group has an exception for the field, the effective object level supplies the default. A field grant is bounded by the effective object Read/Edit capability and never opens an inaccessible record. A missing override inherits; explicit None is an override for a user and contributes no positive grant for a group. Inactive groups, inactive accounts and nonmembers grant no content access. Removing workspace membership removes the user's direct grants and group memberships, journals each removal and advances affected permission versions. Re-adding membership does not reinstate old grants.

Sensitive object types expose a protected system reference field `access_principals` (Zugriffsberechtigte / Access principals), accepting user/group references. Enabling sensitivity appends its JSONB column and creates the field metadata; existing rows receive an empty list. Empty means public only to authenticated workspace users with object access. New records initially list their creator. A nonempty list additionally requires a matching user or active group. Eligible principals have access to the object; Administrators remain globally eligible. Retained references may be removed after their grant/group becomes unavailable, but cannot be newly assigned. Full access is required to explicitly change the list. Disabling sensitivity retains the column, values, field identity and history, makes the field inactive/absent from the form and stops applying the list. It never drops contents. Re-enabling restores the lists. This system field cannot be edited through ordinary definition editors or used to make the entire custom object module-protected.

## Shared enforcement

Every application transaction installs one actor-bound ContentAccess scope after session/account authorization. It resolves rights from current database rows, with policy caching limited to that transaction. API and MCP share this application layer; neither request data nor a claimed agent/user identity can replace the authenticated actor. Permission and membership writes share the existing global/workspace barriers with content reads/writes. A rights change therefore applies to subsequent calls in an existing session.

Record queries apply record predicates before counting, searching, sorting or pagination. Unreadable fields are omitted, and Keyword falls back to the record ID when restricted. Sorting on a restricted field is rejected. Search, heterogeneous workspace lists, Dashboard totals/activity, relationship candidates, Dossier, Primary context and tree branches follow the same rights. Workspace definitions remain readable under configuration permissions without granting content access.

Changes to any explicitly supplied field require its Edit permission, including guessed no-ops on unreadable fields. Complete raw records remain available only inside validation, preserving hidden required values during partial updates. Hidden required input still blocks incomplete creation with an actionable permission error; rights never bypass requiredness or applicability. Readable dependent fields/statuses receive permitted applicability/choice context without the hidden controller value, so their valid inputs remain usable. Returned records are projected after saving. A save that transfers away the caller's record access returns only identity/version and denied capabilities, and the editor closes rather than retaining an accessible form.

Relationship changes require Edit on the source, Read on every changed opposite endpoint and Read on any controlling fields used by their endpoint conditions. Direct writes cannot bypass the candidate selector to probe a hidden condition. Primary association, assignment and linking confer no rights. Invisible links remain stored and are excluded from Dossier/branches; their form control explains that an unavailable connection is retained and cannot be edited. The web client submits only changed editable relationship sides. The backend also rejects attempts to remove a hidden opposite endpoint. Tree ancestor context stops at an inaccessible link; it does not jump through hidden parents.

Journal storage remains immutable. Current record and field rights govern read projections. Relationship history is returned only while both endpoints are readable, and restricted historical Keywords are replaced with identity labels. Filtering occurs before history counts/pagination. Grant changes use the same transaction as per-property journal entries and optimistic version updates. System/permission administration stays Administrator-only.

## UI and remaining work

Object settings expose sensitivity and explain its scope. `configure_object_settings` saves labels and optional sensitivity together in one transaction, checking both definition and permission versions. Designers may save labels; only Administrators may include security changes. All resulting property events share one change ID. The fixed object footer and keyboard submit save both settings; conflicts retain the whole draft. Members & roles and User groups expose the object grant and per-field inheritance/exception editor. Selection changes cannot discard a dirty grant draft. Standard Selects, field groups, shared settings tables/search/pagination and guarded save/reset actions match the rest of the settings UI. Membership/group lists and permission editors occupy separate standard sections. Row actions select and focus the matching principal. The common fixed footer owns permission save/reset actions; dirty drafts block conflicting principal changes. Effective object/field rights identify their winning user/group rules through the same pure resolver used by backend authorization, including object limits and inactive principals. Record-specific restrictions still apply. Mobile field rows stack labels and controls; filtered-empty tables show an explicit message. Removing workspace membership requires a confirmation explaining group/direct-grant removal and retained account/history. Regular users can read configuration; only Administrators can change grants. The record form hides unreadable fields, disables read-only fields and uses the eligible-principal selector for Access principals.

Production external API/MCP credential issuance, lifecycle/erasure, shared module views and physical-device acceptance remain separate work. Relationship/tree reads and permission-filtered journal reads still use the prototype's workspace graph/history scans; measured scaling remains part of release acceptance. No production deployment is implied by local validation.

## Verification and target adoption

Integration/browser coverage exercises group/user grant resolution, field restrictions, record sensitivity, public/creator defaults, revocation, shared API/MCP reads/writes and transactional rollback. Atomic object-settings and permission-editor checks extend those scenarios. The [development verification snapshot](../development.md#recorded-local-verification--2026-11-04) records the latest successful test/build/type-check evidence after correction of two SQL assertion types; this ADR does not assert a green remote CI run.

The expanded PRD model still needs a storage/resolver implementation ADR and an access-preserving migration. Per-principal ownership levels, nested/graded memberships, foreign rules, record privacy/maxima and record-level field exceptions are not provided by migration 8. Retain this implemented baseline until that replacement is explicitly adopted.
