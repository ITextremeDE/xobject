# ADR 0011: Shared workspace appearance

- Status: Accepted
- Date: 2026-10-30

## Context

A workspace needs a shared visual identity. Users keep their preferred light/dark/system mode. xObject already uses shadcn Base UI Nova and semantic CSS variables; design customization must preserve these components and remain available through API/MCP.

## Decision

Store a strictly validated `appearance` JSONB object and positive `appearance_version` on `sys_workspaces`. Existing workspaces receive Neutral, Geist, standard radii and no color overrides through an additive, repeatable migration. Administrators and the workspace's Designers may call `set_workspace_appearance`; ordinary workspace users can inspect the saved settings through `list_workspaces` and the read-only settings page.

Settings contain `baseColor`, `theme`, `chartColor`, optional `primaryColor`/`secondaryColor` (`#RRGGBB`), `radius`, `menuColor`, `menuAccent`, `font` and `fontHeading` (`inherit` or a catalog font). Base colors control surfaces, Theme controls accents and Chart color independently controls `--chart-1` through `--chart-5`. Explicit primary/secondary values take precedence over the Theme. Menu surfaces use the shadcn choices `default`, `inverted`, `default-translucent`, `inverted-translucent`; accents are `subtle` or `bold`. Inverted menus use dark surfaces (as shadcn's dark-class transformation does), even on a light page. Translucent surfaces use a 70% fill and backdrop blur/saturation; bold accents use primary/primary-foreground on menu items. These overrides are scoped to menu surfaces rather than changing general page accents. Heading fonts apply to semantic HTML headings and the standard shadcn heading token, including dialog and card titles. The catalog is pinned to shadcn 4.23.0: eight base palettes, 25 Theme/chart palette choices, five radius choices and its 26 font choices. `default` and `medium` currently use the same 0.625rem radius. These are theme tokens, not switches between Nova/Vega component source styles. No custom fonts, remote font services, CSS strings or arbitrary URLs are accepted.

The web client uses a snapshot of shadcn's paired light/dark registry palettes. Tonal Theme/chart entries come from the base-color registry snapshots; chromatic entries come from isolated CLI `apply --only theme` runs using Nova/Neutral, because the current shadcn init endpoint rejects tonal Theme/chart combinations even though they are in the preset catalog. The live app never calls the registry. Existing saved JSON objects gain missing Theme/chart choices from their previous base palette and inherit their interface font for headings; repeated migrations preserve explicit choices and versions. The column default is updated for newly created workspaces as well. Font names, families and dependencies come from `@shadcn/font-*` registry items. Packages are served locally; alternate font stylesheets load on demand, and browsers request matching subsets. Font licenses ship at `/licenses/fonts.txt`. Catalog updates require reviewing the contracts, palette/font metadata and dependencies together. They do not happen from a remote registry at runtime.

Apply the current workspace's tokens at the document root so portalled dialogs and menus inherit them. Observe personal dark-mode changes and reapply the corresponding palette. Cleanup restores prior root tokens when switching workspace or signing out. Font failures retain system fallbacks. The personal theme controls remain unchanged.

The settings page keeps a draft and shows scoped light/dark samples using the actual standard Button and Input components, semantic headings and five chart-color swatches. Real DropdownMenu and Select examples retain local selection state and include disabled entries. A React context carries the chosen workspace/draft design and preview mode into portals; popup-local CSS variables cover DropdownMenu (including submenus), Select and Command surfaces, while native OS selectors remain native. Caller style overrides and component state styles remain composable. Light previews are isolated from the surrounding personal dark mode. It commits only on Save and retains existing unsaved-change guards. Custom color text uses the higher-contrast black or white foreground, guaranteeing at least 4.5:1 on the solid fill. This calculation does not establish a full accessibility audit of hover, disabled, focus or surrounding surfaces; retain the standard focus tokens and test relevant combinations.

`set_workspace_appearance` requires the current version. A conflicting write returns 409 instead of overwriting someone else's settings. Refresh the workspace query after conflicts; Reset can load the refreshed design without silently replacing a dirty draft. Update the JSON and version and journal each changed property under `appearance.<property>` using one change ID in the common transaction. A journal error rolls everything back. No-op writes produce neither events nor version increments.

## Consequences and verification

There is one saved design per workspace and no personal color/font override. Existing clients adopt saved changes on workspace refetch (including window focus); realtime push synchronization is not implemented. Light/dark mode is still local to the browser.

Tests cover ordinary-user denial, Designer workspace boundaries, API/MCP read/write parity, all font IDs, invalid inputs, no-op/stale writes, concurrent updates, transactional journal rollback, migration retention and solid-fill contrast. Web behavior tests also verify that surfaces, accents, chart colors, heading fonts and manual overrides remain independent. Menu tests cover all surface/accent combinations in both modes, isolation from page tokens, migration retention and journaled API/MCP persistence. Build/typecheck and focused browser checks verify client composition; record any incomplete browser acceptance separately.
