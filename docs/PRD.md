# xObject — Product Requirements Document

Status: Agreed version-1 scope and explicitly planned extensions
Owner: ITextreme
Updated: 2026-11-10

This document specifies the agreed product scope. Requirements below are product decisions, not claims of implementation or acceptance. Unresolved implementation choices are listed in section 10. Version 1 denotes the initial product scope delivered as Community 1.0.0. Later targets are identified explicitly; the quality report records implementation evidence and acceptance limits.

## 1. Purpose and scope

xObject is an open-source application for defining, managing and connecting structured data objects. Configurable modules provide domain models on a shared object platform. Version 1 supplies Contacts & Relations and Projects & Tasks, alongside user-defined object types. Their agreed object catalog is specified below; the [domain-profile appendix](domain-profiles.md) proposes the concrete starting fields and relationships, with remaining implementation decisions identified separately. Documents & Communication is planned for V2; the other deferred catalog modules have no release assignment.

Version 1 includes workspaces, local user accounts, configurable data definitions, permissions, relationships, per-field change history, a recycle bin, tables, forms and record detail views with a Projects-owned Primary hierarchy tree and a dossier. All application capabilities must be available through both API and MCP from the outset.

Out of scope for version 1:

- Documents & Communication, Operations & Finance, IT Service Management, Configuration Management Database, Events & Registrations and Knowledge & Insights as supplied modules. Shared objects explicitly included in a V1 module remain in V1 even if another contributing module is deferred.
- File uploads, attachments and import/export features. API access to individual application operations is not an import/export feature.
- Desktop and mobile applications, SSO, offline operation and data synchronization, including CardDAV/CalDAV.
- Kanban and calendar views.
- General undo. Computed fields require a separate specification and are not included in this delivery baseline.

A paid cloud service is a later offering. The official initial installation target is self-hosting on Linux with Docker Compose.

### 1.1 Product vision and user need

xObject is intended to become a connected work environment for individuals and small to medium-sized teams. People and AI tools should be able to start from a work item, understand its permitted context and previous progress, act on it and resume later from another suitable client. The product should reduce the repeated manual reconstruction of information spread across records, notes, files, conversations and external applications.

The desired continuity covers four stages: finding the relevant starting context, working with complete and attributable information, saving results in the appropriate place, and resuming from the resulting decisions and open work. A useful outcome is that another authorized person or agent can understand what was done, why, which sources were used and what remains, without depending on the original chat or device.

The configurable object platform, supplied modules, Primary hierarchy, Dossier and Journal provide the foundation. The longer-term scope connects structured records with knowledge, source material, decisions, conversations and agent-assisted work. A record can be an entry point even when some related information is held by an external application. Existing source systems can remain authoritative; each information item must have an identifiable leading source rather than competing editable copies. Consolidating more contents within xObject is a long-term option, not an automatic migration requirement.

AI access is part of the product architecture. People and AI use the same application rules and current permissions. Relevant context must be discoverable and retrieved deliberately; connecting a client does not load the whole installation into its model context. The work record should remain useful when the model, client or executing device changes.

Self-hosting, open source, documented interfaces, portable data and manageable administration support user control over the system. Self-hosted storage and model processing are separate choices: sending contents to an external model is external processing and must follow explicit authorization and data-boundary rules.

### 1.2 Delivery boundaries

Version 1 delivers the object, domain, permission and API/MCP foundation specified in this document. Knowledge workflows, cross-source contextual retrieval, user-maintained agent profiles/skills, delegated jobs and automated execution are later targets in section 9.4, with no release assignment. Their acceptance criteria describe intended behavior, not implemented capabilities or additional V1 release gates. The supplied V1 skills in section 9.3 remain distinct from later user-maintained skills and execution management.

Later integrations must preserve the authority and access rules of their source systems. Replacing an existing application, migrating its contents or changing the leading source requires a separate supported transition. Product requirements are independent of any particular personal infrastructure, AI provider or runner implementation.

| Automation | A recurring definition that can generate concrete jobs according to an authorized schedule and missed-run policy. |

| Role | Responsibility |
| --- | --- |
| Administrator | Installation-wide administration and full access to all workspaces and contents, including restricted fields and user-sensitive records. |
| Designer | Assigned per workspace. Configure user-defined types, fields, relationships and their input aids; configure the intended input aids of module fields while preserving protected definitions. |
| User | Assigned per workspace. View workspace settings read-only and use records according to effective permissions. |
| Agent | Act for an authenticated user with that user's effective rights, never a separate privilege grant. |

Administrators assign User or Designer roles through workspace membership. Users can view the entire Workspace settings section, while Designers and Administrators can change workspace configuration. Membership/role assignment remains Administrator-only. Designer status does not grant content permissions. Administrator scope is installation-wide.

Workspace groups have stable workspace-scoped identities. The target model supports user memberships and nested groups with explicit membership rights and cycle rejection. Administrators manage memberships, rights and activation; Designers can create empty groups and rename them, and Users can inspect permitted workspace configuration. A workspace member must not gain installation-wide privileges through a group. Removing workspace access revokes that user's workspace memberships and grants atomically. Inactive accounts/groups and former workspace members do not contribute effective rights; names, references and journal identities are retained. Group lifecycle is described in [ADR 0013](adr/0013-workspace-groups.md); graded/nested memberships and section 4 inheritance are implemented locally under [ADR 0027](adr/0027-ownership-and-foreign-access.md).

### 3.1 Workspace codes and technical names

Each workspace has a freely editable display name and an installation-wide unique technical code chosen at creation. xObject proposes a code; the creator can edit it before saving. Codes begin with a lowercase ASCII letter and contain only lowercase ASCII letters and digits. The code `sys` is reserved for system tables. Workspace codes cannot be changed in version 1.

Object types and fields have immutable UUID identities, readable technical names and separately editable/translatable display labels. xObject proposes English `snake_case` technical names that the Designer can edit before creation. Technical names begin with a lowercase ASCII letter and contain only lowercase ASCII letters, digits and underscores. They are fixed after creation in version 1. Object technical names are unique within their workspace; field technical names are unique within their object type. Supplied module definitions use fixed technical names, reserved against custom object creation even while the module is disabled or planned. Activation must check for conflicting definitions before applying changes; a matching name alone does not identify a shared object type.

An object type's data table is named `<workspace_code>_<object_name>`, for example `itx_contacts`, `itx_projects` or `itx_vehicles` for the workspace **ITextreme** with code `itx`. This uses table prefixes rather than a separate database schema for each workspace. Installation-wide system tables use the reserved `sys_` prefix. Column names remain readable, for example `birth_date` and `commercial_register`.

Creation rejects reserved/conflicting names and names exceeding PostgreSQL identifier limits, including the complete generated table name. System-managed field names are reserved within object types. Display-label changes never rename tables or columns. UUIDs remain the references for definition identity, relationships and journal entries; authorization uses workspace/type identities and permissions rather than table-name prefixes. The backend applies the same naming validation through UI, API and MCP.

See [ADR 0001](adr/0001-readable-workspace-table-names.md) for the naming decision and its consequences. Production access isolation and migration execution, and references beyond the field types mapped in ADR 0007, still require technical design.

#### Selection trees and multiple-choice dialogs

The general custom field kind **Selection tree / Auswahlbaum** (`tree_choice`) supports hierarchical multiple selection independently of Category. Category can also use single, multiple or tree selection. A node has one optional same-dictionary parent. Selecting a child includes all ancestors; deselecting a parent clears its descendants. Selecting a parent alone leaves its children unselected. Active children require active ancestors; cycles, cross-dictionary parents and invalid configurations are rejected.

Multiple/tree fields use a summary field with a selection button and a searchable list/tree dialog. Apply updates the form draft, then the ordinary Save persists it. Defaults follow the same semantics. Existing selections gain required ancestors atomically when a hierarchy changes, with record version increments and one journal entry per changed field. Preserve values on safe flat/tree conversion; reject single-choice conversion when it would discard selected values. Shared UI/API/MCP validation, permissions, history, requiredness and limits follow [ADR 0037](adr/0037-selection-trees-and-choice-dialogs.md).

### 3.3 Languages and physical column order

Technical identifiers and stored business contents are language-independent. Translatable definition names are stored in a `labels` JSONB column on their definition table: `sys_object_types` and `sys_fields`, with Type/Status/Category option labels in the classification JSONB configuration described in ADR 0006. Relationship-type definitions follow the same language-map principle. For example, a field can store `{"de":"Kennzeichen","en":"Registration"}` while its technical column stays `registration`. Definition-label forms show one input with a language selector and per-language translation status; switching language preserves all draft translations until they are saved together. At least one supported-language label is required; German and English are the installed catalog initially. Each workspace independently configures its available interface languages, an active default, and nonempty definition-translation languages. Disabling a definition language retains stored translations and journals; the editor can display retained inactive translations read-only, and API/MCP reject changing or newly adding translations in an inactive language. Adding further languages must not require new per-language columns. Fixed application-interface translations belong in versioned repository resources; the web interface uses i18next under ADR 0004.

`sys_users.language` is an optional preference; null inherits the workspace's `sys_workspaces.default_language`, which initially defaults to English. The explicit user preference applies only when that interface language is available in the current workspace; otherwise the workspace default applies without overwriting the preference. Label resolution tries this effective language, workspace default, English, German and finally a preserved label of unknown language. Definition-language availability governs editing rather than deleting or hiding saved labels. The login page offers the installed interface catalog before a workspace is selected. See [ADR 0012](adr/0012-workspace-languages.md). Record names, Keywords and free text are never automatically translated. Changes to labels and language preferences are application operations with the same permissions and journal rules through API and MCP. Historical journal values retain their original representation.

Timestamp display and input use the optional personal time zone, otherwise the workspace time zone. Store named IANA zones and UTC instants; date-only values remain unchanged. New workspaces propose the browser zone in the UI; API/MCP creation defaults to UTC; configured zones do not rewrite stored instants. Time-zone configuration shares application authorization, conflict and per-property atomic journal rules. DST gaps must be rejected and overlapping clock times require an explicit instant. See [ADR 0014](adr/0014-time-zones-and-regional-display.md). Regional format, date format, 12/24-hour clock, numeric separators and first weekday follow workspace defaults with optional per-property personal overrides. These affect display and never convert stored values or currencies.

For newly created object data tables, physical columns start with `id`, `created_at`, `created_by`, `updated_at`, `updated_by` and `version`. Optional standard fields (Keyword, the Type/Status pair and Category) and user-defined fields are appended when created. They are listed only when installed in the object's field metadata. Routine application operations and upgrades retain existing columns and do not rebuild data tables merely to reorder them or add missing optional fields. Physical column order is independent of form/table display order.

See [ADR 0003](adr/0003-localized-labels-and-column-order.md) for the storage and migration decision. These rules elaborate R-001, R-002, R-008, R-012 and R-034–R-036; they do not introduce new requirement IDs.

Additional structured domain fields follow the staged architecture in [ADR 0032](adr/0032-structured-fields-temporal-values-and-edge-attributes.md); existing scalar Date/Date-time contracts stay unchanged. Structured fields use whole-field rights, typed component values and ordinary per-field journals. Relationship-attribute fields share definition identities and require both-endpoint rights as specified there; attribute-free linking retains its existing endpoint permissions.

Field explanations, creation defaults, scalar uniqueness and record-number rules follow [ADR 0030](adr/0030-field-input-rules-and-record-numbers.md). Defaults apply only on omission at creation, respect field creation rights and never backfill existing records. Unique values remain reserved in the recycle bin. Record numbers are immutable server-assigned values; disabling numbering retains the field and issued values.

### 3.4 Planned conditional field visibility

Status: agreed later extension; not implemented and not assigned to a release. Designers configure **Display conditions / Anzeigebedingungen** in field attributes. A field is always shown by default, or shown for selected Type and/or Status values. Conditions reference stable field/option UUIDs rather than labels; simple AND/OR combinations support cases such as Type “Complaint” AND Status “Closed”. Empty Type/Status values are explicit selectable cases. No script or general workflow engine is implied.

Display conditions are separate from **semantic applicability** under [ADR 0023](adr/0023-record-journal-and-conditional-fields.md). Applicability describes whether a field value is valid for that record and currently rejects nonempty inapplicable values. Display conditions only control presentation and conditional requiredness:

- Hiding a field retains its existing value. Changing Type/Status does not clear, rewrite or fabricate a field value or a field-value journal event. Showing it again restores the retained value.
- A configured required field is required only when both semantically applicable and shown by its display condition. A Type/Status change that reveals an empty required field must complete it in the same save. Other value validation and semantic-applicability rules remain in force, including for retained hidden values.
- Field/object/record permissions remain independent. A display condition grants no access and provides no confidentiality boundary. Authorized API/MCP reads may still return a form-hidden value; hidden fields are not automatically forbidden API/MCP inputs. All channels share the condition configuration and backend enforcement of conditional requiredness, validation and permissions.
- Definition changes use the established optimistic versions, dependency protection, existing-record preflight and atomic definition journals. Renaming Type/Status options retains their references. The later implementation must define safe handling of removal/deactivation and reject ambiguous or cyclic dependencies.

Acceptance examples: hide a populated field by changing Type, save and reveal the unchanged value again; combine Type/Status conditions; handle explicit empty selections; require a newly revealed empty field; preserve rights restrictions through UI/API/MCP and record no synthetic value changes merely for hiding/showing. The current installation needs no speculative schema columns or compatibility paths; the metadata/editor extension is implemented when this feature is scheduled.

## 4. Permissions

### 4.1 Target model and delivery boundary

The model combines object/field permissions, ownership through Access principals and foreign access through user/group rules. This section is the product authority. [ADR 0027](adr/0027-ownership-and-foreign-access.md) describes the local implementation, resolver, storage and current installation, extending the earlier ACL in [ADR 0026](adr/0026-content-permissions.md). Calendar availability/time-only mutations and notification delivery remain separate future capabilities; reserved levels do not expose additional contents or implement a calendar. Reproducible validation and public evidence are described in [development](development.md#verification-and-acceptance); they do not establish release or production acceptance.

The product deliberately keeps installation-wide Administrator content access. User/Designer are workspace configuration roles and confer no content rights. All other grants and inheritance are workspace-scoped. Agents use their authenticated user's current effective rights through the same application layer as UI and API.

### 4.2 Object and field permissions

Administrators configure which object types each user/group can use and optional field exceptions. Object sensitivity is configured once per object type; activities are always sensitive, including Projects, Cases and Tasks. A non-sensitive object has no record-level participant restriction; every user authorized for that object can use its records within the applicable object/field limits. A sensitive object additionally evaluates ownership or foreign access for each record.

Object permissions use the content capability levels in section 4.3 as a ceiling; a separate Create capability controls whether new records may be created. Create alone exposes no existing record contents. Missing user Create settings inherit active group grants; an explicit user setting overrides that result. For non-sensitive records, the object ceiling directly determines available record actions. For sensitive records, the resolved record level additionally limits those actions. Rights on an existing record do not independently authorize creation of unrelated records. Field permissions are None, Read and Edit; Edit includes Read. Full access on a record does not override object or field restrictions. Duplication requires creation rights and a valid new record; it must not copy unreadable fields or create records with missing inaccessible required input. The web action opens an editable unsaved creation draft; preparation allocates no record identity, record number or journal event. Saving rechecks current Duplicate/Create rights and the source version before normal atomic creation. Unique/derived values, record numbers, ownership and relationships are not copied.

Active group grants combine by the highest applicable right. Explicit user object/field overrides remain available as administrative restrictions and replace the corresponding group result; an absent override inherits, while explicit None denies that capability. This is distinct from record ownership precedence below. If filtered grants are introduced, their field allowances stay tied to their own record scope: a broad object grant from one group must not extend a different group's narrowly scoped field allowance. These rules apply independently of the ownership and foreign-access resolver. Optional per-record field exceptions can further restrict Read/Edit for a user or group without increasing administrative object/field ceilings or bypassing record access. Their direct-user/group precedence follows the same explicit-override rules; an absent record exception inherits. Record-level Full is required to manage these exceptions within the caller's own authority. Protected security metadata must not become an alternate way to administer global/workspace grants.

### 4.3 Record rights and calendar visibility

The following content levels are cumulative. Each level includes the preceding content capabilities; None grants no access. None is an administrative object/field or foreign-access setting, not an active ownership entry. Available actions are the intersection of the content level, object ceiling, applicable field permissions and lifecycle/configuration rules. Full content access grants no configuration, account-security or protected-module privileges.

| English / German | Meaning |
| --- | --- |
| Read / Lesen | Open an accessible record and read permitted fields. |
| Read and duplicate / Lesen und duplizieren | Additionally duplicate permitted contents, subject to target creation rights and validation. |
| Change times / Zeiten ändern | Additionally change the explicitly designated scheduling fields of calendar-capable records without editing unrelated content. |
| Edit / Bearbeiten | Additionally change permitted record contents. |
| Edit and delete / Bearbeiten und löschen | Additionally move the record to the recycle bin. |
| Full access / Vollzugriff | Additionally restore, permanently delete with confirmation and manage Access principals within the caller's effective authority. |

Calendar availability visibility / Kalenderbelegung sehen is an additional **foreign-access** capability below Read. It exposes only an authorized busy interval (start/end), not the record, Keyword, participants or other contents. It does not permit opening the record or changing times. Keep availability projection separate from ordinary record reads and from the higher Change times level. It has no effect on objects without designated scheduling fields. Calendar views, availability projection and time-only editing remain later delivery with the calendar feature, outside version 1; generic date fields do not automatically become scheduling fields.

### 4.4 Access principals, ownership and activity involvement

The protected field remains named **Zugriffsberechtigte / Access principals**, technically `access_principals`. Activities are always user-sensitive; this includes Projects, Cases and Tasks in V1. Module provisioning enables sensitivity and supplies the protected Access principals field. Administrators cannot disable activity sensitivity through UI, API or MCP. Future activity profiles follow the same invariant. Each entry references a workspace user or group by stable identity and carries an ownership level. On non-activity records the list denotes ownership/access participation, not a work assignment. On activities such as Tasks and future Phone calls, the listed users/groups are the people/team involved in performing the activity and the default notification audience. A participating group represents team work; it does not assert that every member must separately complete the activity. Per-member completion tracking is a separate, unspecified feature. Read-only participation is possible.

New sensitive records initially include their creator with Full ownership, bounded by object/field rights. A participating group's ownership is bounded by each member's membership level, including nested membership limits. A nested membership path is limited by its lowest membership level and the group entry's ownership level. Several group-derived ownership paths combine by their highest permitted result. Inactive or removed intermediate memberships contribute no path. A direct user ownership entry takes precedence over group-derived ownership, even if lower. If ownership exists, it takes precedence over foreign access, even when foreign access would be higher. An inactive/unavailable principal cannot be newly selected; retained references remain identifiable without conferring rights.

Only eligible users/groups with access to the object can be newly selected. The selector uses authorized workspace identities and object eligibility; foreign access to someone's records is not an additional prerequisite for selecting that eligible person. Selecting a group keeps one dynamic group entry; expanding it deliberately creates individual entries, whose later participation no longer follows membership changes. These two actions must be clearly distinguished. Full access is required to edit the list. A caller cannot delegate a level or capability beyond their own effective authority or bypass administrative object/field ceilings. Changing Access principals changes involvement and rights together; it must explain loss of the caller's own access before saving. Removing the creator delegates participation to the remaining principals. The creator retains only rights obtained through the normal current resolver, including explicitly configured foreign access. There is no hidden perpetual creator grant after the creator is removed. This also applies after repeated delegation; historical creator metadata never supplies a grant.

An empty list continues to mean public within the authenticated workspace, subject to object/field rights. The UI makes this explicit as **All (workspace) / Alle (Arbeitsbereich)**, not anonymous Internet access. The current policy represents workspace-public mode and its ownership level explicitly, bounded by object/field ceilings; it never infers a grant from missing policy metadata. Clearing the last entry explicitly returns to this workspace-public mode and requires the normal Full/delegation checks and a visibility warning. An explicit public level can later be lowered within the caller's authority. In public mode, direct user ownership takes precedence, followed by applicable participating-group ownership and finally the public fallback; foreign access does not override a lower ownership result. A nonempty list whose users/groups become inactive or unavailable never turns public automatically. Public visibility alone does not assign work to every member or subscribe the whole workspace to activity notifications.

Access principals are the single source for activity participation and work assignment, including Task assignees. The supplied Task has no separate Assigned to field or assignment storage. Responsible person denotes coordinating responsibility and grants no content rights. Ownership changes use the shared security writer and are journaled atomically; foreign access grants rights without adding activity participants or assigning work.

### 4.5 Foreign access and inheritance

Administrators configure requester → owner rules between workspace users/groups: for example, Hans may Edit Clara's records, or Sales may Edit Administration's records. Each rule has a default level and optional per-object overrides; absent access grants nothing. A missing per-object override inherits the rule default, whereas explicit None disables that rule for the object. Defaults do not span workspace boundaries. The default per-record maximum is Full, which caps an existing foreign grant but never creates one. The inverse “Access from others” view edits the same rule, not a second competing permission. Foreign readers/editors do not become participants, assigned workers or default notification recipients. For example, Hans → Clara Edit allows Hans to edit Clara's Task while Clara remains the participant/work recipient; Sales → Administration similarly permits Sales to work on Administration-owned contents without assigning Administration's work to Sales.

Group inheritance applies on **both sides**. A requester inherits its groups' foreign access, and a rule targeting an owner group covers records directly assigned to its members as well as records assigned to that group. Thus Management → Sales applies to a record directly assigned to Hans when Hans is a Sales member, even though neither Sales nor Management is in the record's Access principals. Martin inherits the rule as a Management member. Nested groups are supported; cyclic group membership is rejected.

Transitive foreign-access paths must also be represented explicitly in the resolver design rather than accidentally lost: if E has foreign access to A and A to D, E can have inherited access to D's records through that authorized path. For a given object, each path takes the least permissive of its applicable foreign grants and graded memberships; only actual ownership entries can terminate a path. A direct ownership restriction on an intermediate user cannot be bypassed by pretending that user has a higher foreign right to that record. Record privacy/maximum and the requesting user's object/field ceilings are applied to the resulting action. Inheritance cannot turn an intermediate user's mere object permission or historical creator identity into ownership. Confidential access cannot be forwarded along a path that lacks the separately required confidential capability. These are explicit xObject evaluation rules; the implementation ADR must specify the finite graph resolution and verify the precedence cases before delivery. Multiple eligible foreign-access paths combine by their highest permitted result. Cycles must terminate and must not create an initial grant or escalate rights. Group membership alone must not silently grant access to coworkers' individually assigned records: mutual access is an explicit group-to-itself foreign-access rule. The UI must explain the winning path and relevant limits.

Administrative inheritance controls must distinguish direct rules from group-derived rules. If group-derived foreign access is disabled for a user, that user's direct foreign rules still apply; inherited grants must not survive through another equivalent group path. Membership, activation and rights changes take effect on subsequent operations in an existing session, without requiring sign-out.

### 4.6 Per-record foreign-access limits

Each sensitive record has a maximum foreign level plus a privacy mode (Normal, Personal or Confidential). Normal is the creation default; its maximum defaults to Full without granting anyone access. The limit applies to every direct and inherited foreign-access path, never to ownership:

- A normal maximum level caps the actions available through foreign access.
- **Personal / Persönlich** excludes foreign access; only ownership and the explicit installation Administrator exception remain.
- **Confidential / Vertraulich** requires a separately granted confidential-access capability in addition to the ordinary foreign level and object/field rights. It is not an extra level granting Full access.

Public mode cannot simultaneously be Personal or Confidential: the UI and backend reject this combination and require explicit non-public owners before such privacy can be saved. Clearing the last owner of a Personal/Confidential record must ask for an explicit change to public Normal mode rather than silently exposing it. Changing the maximum or confidentiality is a permission change subject to the same Full-access/delegation limits and journal rules. The future calendar has an independent, explicitly configured workspace privacy policy for busy-time disclosure on Personal/Confidential records. Until configured, no such projection is exposed. When permitted, it reveals only a generic busy interval, never titles, participants or contents. Ordinary record endpoints still deny access; availability-only users do not contribute ordinary readable-record counts or journal results. xObject's Administrator exception is intentional and differs from ordinary ownership and foreign access.

### 4.7 Notifications, defaults and administration

Activity notification rules normally address explicitly participating users and eligible active members of participating groups, after resolving their current access (at least Read). A participant list defines recipients; it does not by itself cause an email for every edit. Event selection, own-change handling and delivery preferences belong to the later notification design. Merely obtaining foreign access does not subscribe a user. An explicit later subscription/rule may notify a foreign-access user who has the required current rights; this never adds ownership. Member delivery is the target default for participating groups and deduplicates users reached through several groups or direct participation. A configured shared group destination is an optional later delivery mode that requires an explicitly authorized content policy; it cannot be treated as a user with permissions or bypass members' field restrictions. Delivery failures do not roll back a successfully saved business record; reliable queuing/retry requires the later notification design. Public records do not broadcast automatically. Scheduled jobs re-evaluate current rights before exposing contents; payloads must not include restricted fields. Mail delivery, alarms and notification subscriptions remain later work, not a version-1 delivery claim.

A STANDARD user/group template is a creation template, not a universal group or an automatic grant to all users. A user's default group, if configured for creation defaults, is a separate concept; it must not silently add owners or widen access on existing records. Concrete template/default-group behavior must be designed before enabling it.

Only Administrators configure security policy, foreign grants, graded/nested memberships and sensitivity. A user-facing ability to change general foreign access on one's own records is not enabled implicitly; it requires a separate explicit Administrator delegation setting and remains bounded by administrative ceilings. Workspace/instance security-administration authorization cannot be obtained merely through a foreign Full grant on a business record. Designers continue to configure object definitions, fields and input aids. Record-level Full holders manage their record's Access principals and foreign-access limits within the above ceilings. Settings must expose effective rights with their source, direct/inherited status and limiting rule, so “may edit” is distinguishable from “is participating”. Previews must use the same resolver as actual authorization.

Permission, membership, public/private, participant and foreign-limit changes are versioned, atomic with one journal entry per changed property and a common change ID. Current rights govern historical projections; immutable stored history is not rewritten when ownership changes. Restricted contents must not leak through search, counts, filters, sorting, Dashboard, relationship candidates, Dossier, Primary tree/context, journals, notification payloads or error messages. Primary/General/custom relationships never confer content rights.

### 4.8 Migration and verification

The application serves one current installation model under ADR 0028. Community 1.0.0 and 1.0.1 are published and share the same schema/catalog/auth fingerprint. Development databases are recreated from that baseline, with no older-schema adoption or compatibility behavior. Each sensitive record has exactly one security policy; its virtual Access principals field is derived from the graded owner entries. Enabling sensitivity initializes policies for currently unrestricted records as workspace-public; disabling sensitivity on non-activity objects requires explicit Administrator confirmation and retains their policies for re-enabling. Activity sensitivity cannot be disabled. Backup/restore and fail-closed maintenance are specified in ADR 0035; the supported 1.0.0 → 1.0.1 upgrade verifies the unchanged target fingerprint and integrity. Future schema-changing released upgrades require dedicated migrations and acceptance before publication.

## 5. Relationships and primary association

General relationship types support 1:1, 1:n, n:1 and n:m. Each side's maximum cardinality controls display: at most one partner uses a selection field; multiple possible partners use a list. Minimum cardinality determines whether a relationship is required.

The General relationship belongs to the application core. The Contacts module supplies the Contact-person / Organization relationship; the Projects module supplies Primary association for all object types while enabled. These are distinct relationships: a Contact person’s Organization does not count as its Primary association. Projects activation and its fixed base-object installation are implemented under [ADR 0021](adr/0021-relationship-scope-and-projects-module.md). Contacts activation already provisions Contacts, Distribution lists and their supplied relationships. Shared object/field contributions, common forms, retained activation/deactivation and additive template updates are implemented; remaining domain profiles and future schema-changing released upgrades need separate specification and acceptance; a matching technical name alone must never convert a custom definition into a module-owned one.

The two protected system types are: Primary association (directed, at most one direct parent) and General relationship (undirected, optional/unlimited). Custom types each connect exactly one left and one right object type; they may be directed or undirected, with names for both sides and per-side minimum/maximum cardinality. Used object pairs and direction remain fixed for consistent historical reporting. For symmetric undirected endpoints, both sides use identical labels and cardinalities. [ADR 0018](adr/0018-relationship-type-definitions.md) specifies definitions; [ADR 0019](adr/0019-record-relationships.md) adds record connections, explicit activation/preflight, cardinality enforcement and selection/list controls. [ADR 0020](adr/0020-relationship-tree.md) adds the tree and derived ancestor display; object-level required associations/ancestor levels are implemented under ADR 0024.

Object settings expose a workspace-local `primaryRequirements` configuration: `associationRequired` requires at least one direct parent; `requiredLevels` independently selects Contact, Project and/or Case from the levels permitted above that object. An inherited level satisfies the same requirement as a direct one. Selected levels imply a parent even if `associationRequired` is false. Defaults are false/empty. Administrators and Designers configure these rules through the same versioned `configure_object_settings` operation as labels/numbering; each changed property has its own definition-journal entry in one change group. Stricter rules preflight all retained records, including recycled records, under the shared model lock. Every relationship write validates the final retained graph, including descendants affected by ancestor changes; ordinary create/update, linked creation, duplication and restoration use the same rules. Violations roll back contents, edges, versions and journals together. Requiredness uses structural UUID paths regardless of the actor's read access and never grants access. Recycling retains the parent/edges and still satisfies structural requiredness; hidden/recycled context stays unavailable in the authorized UI projection. Required Primary elements remain visible in the effective form/designer. A refused configuration/write reports the required-context conflict without disclosing hidden records.

Saved, editable records offer two object-first header dropdowns: **Link with…** selects existing records; **New linked record** opens the normal creation form with a preselected source relationship. General-only objects are direct items; objects with additional eligible relationships have a submenu using the existing General label and side labels. Record and link creation is atomic; cancelling creates neither. Rights, endpoint conditions, cardinalities and source/definition versions apply equally through UI, API and MCP. See [ADR 0019](adr/0019-record-relationships.md).

Missing record levels are allowed unless the source object requires them. Details shows single-value fields with Choose/Change, Open and Clear controls for every available level, disabling unavailable actions. #### Planned Contact-kind conversion workflows

Status: planned for V2, outside the accepted V1 CRM scope; detailed design and implementation remain outstanding. Normal Contact updates keep their kind immutable. Dedicated guided actions from the record actions menu will handle these conversions:

| Action | Result |
| --- | --- |
| Form organization → new Organization / Firmenbildung → neue Organisation | Create a new Organization and convert the existing Individual contact into its Contact person. The existing Contact retains its identity; the new Organization receives its own identity. |
| Form organization → existing Organization / Firmenbildung → bestehende Organisation | Convert the Individual contact into a Contact person of the selected existing Organization. |
| Continue as Individual contact / Als Einzelkontakt weiterführen | Convert the Contact person into an Individual contact and remove its Organization membership. |
| Reverse organization formation / Firmenbildung aufheben | Convert all Contact persons belonging to the selected Organization into Individual contacts and remove their Organization memberships. |

The last action is a new business operation against current records, not a restoration of earlier snapshots: other Contact persons or changes may have been added since formation. The Organization remains available and can be deactivated separately. Ordinary Organization replacement/removal without changing Contact kind remains a distinct existing operation.

Common rules for the guided workflows:

- Preserve existing Contact UUIDs, record numbers, history, security policies and compatible relationships, including Identities and Distribution-list membership. The operation itself grants no additional content access.
- Show a preview of the resulting records, Contact kinds, Organization assignments and the proposed mapping of company/personal fields before confirmation. Existing Organization values are overwritten only after an explicit decision. No incompatible value or relationship is silently discarded.
- Collect missing target-kind required values before conversion, including a personal Last name when an Individual contact previously represented only a sole business. Recalculate derived names using the existing rules and the resulting Organization assignment.
- Check current authorization, record/definition versions, requiredness, field applicability, uniqueness, relationship cardinalities and endpoint conditions against the complete resulting state. Conflicts must be resolved before execution; hidden values remain protected.
- Save the complete confirmed operation atomically, including all affected Contact persons and the new Organization where applicable. Journal every field and relationship change under one shared change ID, retaining before/after Contact kinds and record identities. Failure leaves all affected records unchanged.

Before implementation, specify exact field mappings and the required operation/field permissions, handling of incompatible custom fields/relationships and concurrent membership changes, plus acceptance cases for restricted users and the multi-record action. These details do not authorize automatic copying or overwriting of Organization data. UI, API and MCP must use the same dedicated workflow and transaction rules.

### 6.4 Standards-aligned contacts, calendars and tasks

The domain profiles for Contacts, Distribution lists, Appointments, Vacations and Tasks must support an explicit, vendor-neutral standards mapping. This is an accepted model-design constraint, not implemented import/export, synchronization, calendar UI or a claim of full RFC conformance. [ADR 0031](adr/0031-standards-aligned-groupware-models.md) records the architecture and reference specifications. Existing requirement IDs remain unchanged; this elaborates R-003–R-006, R-012, R-024–R-029 and R-041.

| Object | Standards basis | Required model distinction |
| --- | --- | --- |
| Contacts | vCard 4.0; JSContact as an additional JSON reference | Structured name components and formatted name; repeated labeled/preferred emails, telephone numbers and international addresses; birthdays with an unknown year. Map Contact kind, Organization relationship and Identities explicitly; CRM Keyword is not necessarily the formatted contact name. |
| Distribution lists | vCard group cards (`KIND:group`, `MEMBER`) | Explicit group identity and membership references, separate from contact categories, user/security groups and mail delivery. |
| Appointments | iCalendar `VEVENT`; JSCalendar `Event` as an additional JSON reference | Date-only versus timed values, event time-zone semantics, exclusive end, recurrence master/occurrence exceptions, organizer, attendees, participation response, event status and free/busy effect. |
| Vacations | Calendar projection using `VEVENT` | Retain the Vacation record identity and project its absence interval with the same date/time rules as Appointments. Leave application, approval and entitlement are separate domain behavior, not calendar status. |
| Tasks | iCalendar `VTODO`; JSCalendar `Task` as an additional JSON reference | Optional start/due values, date-only versus timed values, progress, completion timestamp, recurrence identity and explicit mapping of configurable status/priority. Task status and attendee response remain distinct. |

The [appendix](domain-profiles.md#standards-aligned-profiles) provides concrete proposed fields, rules, forms and acceptance cases; [ADR 0032](adr/0032-structured-fields-temporal-values-and-edge-attributes.md) now defines the structured storage/contract architecture, with nine Contact codecs and relationship attributes implemented locally; the common temporal codec is implemented; recurrence/calendar parties and complete exchange-profile coverage remain open. The selected collection model uses typed structured fields under ADR 0032; generic Date/Date-time fields do not by themselves represent partial birthdays, domain time zones or recurrence exceptions. A partial birthday must not invent a year. UTC instants alone do not preserve a recurring event's local-time intent. Personal display-zone changes must not rewrite an event's zone; floating local times require an explicit supported representation or a reported unsupported value, never silent conversion using the viewer's zone. Existing timestamp API rules in section 3.3 remain unchanged until dedicated domain contracts are specified.

Define each supported standard profile before claiming support: exact versions/extensions, mandatory and optional properties, cardinalities/types, field and relationship mappings, configured status/priority mappings, unsupported-data behavior and observable round-trip acceptance. Consider current vCard extensions and task extensions explicitly, without assuming every published extension is implemented. JSContact/JSCalendar are complementary design references; selecting them does not silently replace the existing application API contract or promise JSON exchange endpoints.

Future synchronization uses CardDAV for contacts/groups and CalDAV for calendar events/tasks, subject to the peer's advertised capabilities and tested profile. Plan explicit mappings to remote address books, calendars and task collections; stable exchange UIDs and per-connection external identities/versions are separate from record UUIDs, record numbers and optimistic versions. Define conflict resolution, deletion propagation and prevention of duplicate/echo writes before enabling bidirectional writes. The eventual connector's writes must use the shared API/MCP application rules and journals with the acting user's current rights.

Product-specific behavior must not redefine the domain model. Nextcloud is one possible interoperability test peer, not the specification authority or a required dependency. A peer that exposes contact groups differently does not make Distribution lists into Categories in xObject. Unsupported mappings must be visible; preserve xObject-only fields/relationships and safely retained external properties, or refuse a destructive round trip instead of silently dropping or reinterpreting values. External attendees, group members, sharing flags and privacy classifications never grant xObject permissions automatically. External references do not enable uploads, remote resource fetching, reminders or invitation delivery implicitly.

Acceptance for domain delivery checks preservation of structured/repeated contact data, unknown-year birthdays, explicit group membership and separation from categories; date-only/exclusive-end intervals, domain-zone intent across DST and viewer-zone changes, and recurrence/exception identity; and tasks without dates with distinct progress/completion/status semantics. Future synchronization acceptance additionally checks stable identity, round trips, stale/conflicting updates, deletion handling, peer capability limits, permission enforcement and retention of unmapped data. These are acceptance targets, not completed tests. Transport, import/export, calendar views, scheduling messages and notification delivery remain outside V1.

### Permanent deletion and retained history

The recycle bin retains the complete record, relationships, security and journal and supports authorized restoration. Confirmed permanent deletion removes the live contents and operational links and ends restoration through the application; it does not erase journal contents. Retained journal/identity references must not keep the record in normal lists, selectors, relationships or cardinality slots. Dependent records are not deleted in a cascade. Required-context and other dependency conflicts must be resolved explicitly before deletion can commit.

The retained history is visible in full only to installation Administrators. For all other users, including Designers and object-level Full users, any otherwise visible event referring to the permanently deleted record is projected as a neutral “Record deleted / Datensatz gelöscht” notice. This applies equally in the deleted record's retained history, system-journal projections and surviving linked-record journals. No historical values, names, numbers, relationship attributes or deleted-record security contents are disclosed through alternate detail views or query channels. Existing authorization still controls whether a context/event is visible at all; a tombstone is not a new directory of deleted records. The minimal identity/authorization metadata required for that decision may be retained separately from live business contents. Other records' unrelated journal entries remain unchanged.

Deletion, operational edge removal, reduced deletion-event creation and the retained-history visibility boundary must commit atomically. Normal journal entries remain immutable. A separate content-and-history erasure capability may be evaluated later; it is not part of this deletion operation or the V1 delivery commitment. The confirmation must explicitly state that Administrators retain access to the history. R-039/R-040 are implemented locally: the registry stores a deletion timestamp/actor, retained policy and frozen field/event/context eligibility; the live row and edges are removed. Current rights and frozen prior eligibility jointly govern non-Administrator deletion notices. Full retained history is available through the Administrator history area in the recycle bin and the shared API/MCP journal operation.

The Administrator history overview identifies deleted records with their last display Keyword, retained as private tombstone metadata before live deletion, including derived Contact names. It supports Keyword/ID search, object filtering and sorting before counts/pagination, and uses the shared Journal for field/relationship inspection. This caption is never exposed in ordinary users’ deletion notices.

### 9.1 Delivery conventions

- Local development uses a monorepo with `apps/web`, `apps/server`, `packages/contracts`, `deploy` and `docs`; these directories contain the application source; the independent public website lives in `apps/site`. Their existence is not evidence of a release package.
- GitHub is the leading public remote. The second Forgejo remote is private. Push intended branches/tags separately to both and verify them independently; do not maintain divergent development histories or assume Git transfers platform metadata.
- OpenProject owns operational planning. Git owns this PRD, glossary, ADRs, source, configuration, documentation, changelog and public roadmap. Detailed task status does not belong in this PRD.
- Use Conventional Commits, Semantic Versioning, Keep a Changelog, ADRs and Diátaxis as established project conventions. Use IREB/CPRE terminology and a product glossary.
- Public entry points: Documentation at `https://docs.xobject.org/`, Changelog at `https://xobject.org/changelog/` and Roadmap at `https://xobject.org/roadmap/`. The application sidebar links to them above the user menu, opening a new tab. URL selection is distinct from publication of these pages.
- Public product website: Astro. Public documentation: Astro/Starlight. Both are static sites delivered with Caddy. `CHANGELOG.md` and `ROADMAP.md` are reused rather than maintained as duplicate copies. The public roadmap is curated from OpenProject.
- Releases have explicit tags, reviewed release notes, tested images, Compose configuration and upgrade/restore instructions. Supported documentation versions remain accessible under versioned paths. GitHub platform metadata needs a separate backup mechanism.
- Work in small end-to-end changes, review through pull requests and validate relevant acceptance criteria. No performance target, supported-host matrix or scalability claim is established until measured and specified.

Personal settings are ordered Profile, Account & security, Appearance, Language & region. Profile edits the own display name; Account & security shows the read-only sign-in email. Profile-name changes use the common journaled API/MCP operation. Personal Account & security settings allow verified local password changes and management of the signed-in user's own active sessions through the same API/MCP rules, without exposing bearer credentials. Current sessions are protected from the other-session revocation actions. See [ADR 0010](adr/0010-account-security.md) for the local implementation and remaining production authentication decisions. This elaborates R-042 and the journal rules without adding a requirement ID.

Workspace Appearance is shared by all users of that workspace. Administrators and its Designers configure a shadcn base color scheme, a separate accent Theme, an independent chart palette, separate optional six-digit hexadecimal primary and secondary overrides for Light/Dark, corner radii, an interface font and a heading font from the fixed shadcn-based catalog, including locally served Orbitron. Headings can inherit the interface font. A fixed Lucide icon identifies the workspace in its switcher; an own-logo upload is visibly prepared but disabled until image storage/upload exists. Menu surfaces support standard/inverted (dark), each optionally translucent, and subtle/bold menu accents. Interactive light/dark previews use real standard sidebar, card, table, input, button, dropdown and selection components, including keyboard navigation, active/selected states and disabled entries. Portalled preview menus use the draft interface font and mode. Inline advisory checks flag insufficient custom-primary contrast for normal links and focus borders; they do not change the configured colors. Menu settings apply to the current workspace's dropdowns, Select popups and command palette; native platform selects retain their native popup rendering. Custom font uploads, external font services, arbitrary CSS and component-style switches are excluded. The UI previews light and dark locally; Save publishes the shared design, while Reset restores the current saved state. User and header light/dark/system mode remain personal and browser-local. Workspace changes must replace the previous workspace's tokens, including portalled overlays; leaving the application restores the default design. API/MCP enforce the same workspace authorization, strict values and optimistic version checks, with one journal entry per changed property and atomic rollback. A no-op does not increment the version or create journal entries. See [ADR 0011](adr/0011-workspace-appearance.md).

### Installation setup and deferred profile features

The container installation creates the first Administrator through a one-time interactive setup command inside the application container. The operator supplies name, email and password, with hidden password input, then signs in normally. There is no shipped default account or public first-visitor claim flow. The local `npm run admin:create` and container `setup` commands share the same atomic first-account writer. Environment variables are supported for controlled automation; an existing installation cannot be claimed again. See [the operator guide](self-hosting.md).

Changing the sign-in email is deferred until outgoing email is available. The agreed flow requires the current password and an available new address, sends a single-use expiring confirmation link to the new address, retains the old address until confirmation, then atomically updates/verifies the email and journals the change. Notify the previous address and revoke other sessions after completion. User identity, permissions, relationships and history retain the same user ID. The mail flow, delivery/retry handling and corresponding shared API/MCP operations remain later implementation work; the current profile email stays read-only.

The Profile page reserves a profile-picture area with an initials fallback and an explicitly disabled upload action. Upload, storage, validation, removal and application of an image remain deferred until the upload facility exists. The existing auth `image` field is not currently used to load external image URLs. This visual preparation does not add file uploads to the current implementation or alter the general version-1 exclusion of uploads/attachments.

### 9.2 MCP interoperability and V1 acceptance

R-041/R-042 require a provider-neutral MCP interface. Protocol compatibility depends on the connecting client, its negotiated protocol revision, supported capabilities, transport and authentication, together with a model capable of tool use. A provider/model name alone is not a compatibility guarantee. Keep the xObject API version independent of the dated MCP protocol revision.

The current local implementation uses the official TypeScript server/client SDKs 2.4.0, MCP 2026-07-28 discovery/envelopes and the SDK's stateless 2025-era serving, personal Bearer credentials and resource-bound OAuth authorization, shared-contract output schemas, structured results and JSON text. Protocol and permission-aware Skills tests use real SDK clients. Passing local integration tests is not provider end-to-end acceptance. The following delivery criteria distinguish implemented protocol behavior from remaining provider work:

- Align the implementation with MCP 2026-07-28 using a supported official SDK, including discovery, request/version metadata and result envelopes. Record the exact SDK/client/model/protocol tuple used during acceptance; verify supported-version negotiation rather than assuming every client already implements the latest revision. Avoid bespoke compatibility transports or provider-specific business rules.
- Add the MCP HTTP authorization profile: OAuth 2.1 with Authorization Code/PKCE, protected-resource and authorization-server discovery, appropriate client identification/registration, resource/audience-bound tokens and safe consent/expiry/revocation behavior. OAuth-issued access must resolve to an xObject user and the same live permissions/journal rules. Keep personal credentials for explicitly configured clients. This requirement does not depend on external SSO; SSO remains later scope. **Unreleased correction planned for 1.0.2:** offline consent must survive natural browser-session expiry and cleanup. Successful refresh rotates the token and restarts its seven-day validity period; explicit sign-out/session revocation, password change, user deactivation and application revocation terminate delegated access. ADR 0034 owns the authorization refinement.
- Expose tool output schemas and structured results consistent with the shared contract, retaining JSON text where required by the supported protocol/client. Supply actionable descriptions and accurate read-only/destructive/idempotency hints. Annotations and client approvals never replace backend permission checks or required destructive confirmations.

V1 live provider acceptance is limited to OpenAI. Codex with an available tool-capable OpenAI model is the primary acceptance path. ChatGPT plugin/app integration is an additional path when the account/workspace enables it; a Responses API run is additional coverage only with separately available API access. An existing OpenAI subscription does not prove API access or availability of every product feature. Do not purchase additional provider subscriptions or infer coverage for unavailable paths. Protocol/contract tests with the official MCP SDK remain provider-independent and require no model subscription.

Acceptance covers discovery/tools/resources where supported, structured successful results and errors, read/search/create/edit/link/lifecycle operations, current User/Designer/Administrator and field limits, read-only credentials, token expiry/revocation and journal provenance. Use fictional test data and reviewed user-bound credentials. Client-side confirmation and backend destructive confirmation are checked independently. Cloud-side tests need an explicitly authorized reachable HTTPS endpoint or supported private-connectivity path; a service bound to localhost is reachable only from a local client without such a path. Capture the tested client version, model, negotiated revision, transport/authentication, supported features and results; report unavailable capabilities as not tested. The primary live Codex path has passed the recorded [provider exercise](quality-acceptance.md#provider-acceptance); its exact client/model/protocol and supported skill paths define the accepted scope.

Anthropic Claude and Google Gemini offer MCP-capable client/API paths, but remain documentation-assessed and untested for xObject. Their model variants, hosting paths and optional capabilities are not part of V1 acceptance. Additional providers can be validated later without changing the business model or weakening permissions. See the [client compatibility reference](api.md#client-compatibility-and-acceptance) for sources and current boundaries.

### 9.4 Later target — connected context, knowledge and agent work

The requirements in this section elaborate the product vision beyond V1. They are not implemented delivery claims, have no assigned release and do not alter R-001–R-048 or the V1 acceptance scenarios. Detailed contracts and architecture decisions are required before implementation. Existing integrations, schedulers, source repositories and execution tools should be reused where they satisfy these requirements; this PRD does not select a second search engine or a new agent runtime.

#### Context and knowledge

| ID | Requirement | Later acceptance criterion |
| --- | --- | --- |
| R-049 | An authorized user or agent can obtain a bounded working context from a record, including relevant relationships, source references, decisions, results and open work. Context discovery is available through UI, API and MCP. | Starting from a Contact, Project or another supported record identifies the leading sources and relevant permitted context without requiring the caller to know each storage location. A context package identifies its retrieval time, available source versions, freshness limits and omissions. Unavailable or stale sources are explicit; they are not represented as complete current knowledge. |
| R-050 | Context discovery combines exact full-text/identifier lookup, semantic retrieval and relationship traversal with meaningful filters and attributable results. Current source and field rights apply before previews, counts and context assembly. | A question about a previous decision can return its rationale, supporting sources and related work. Results show source links and understandable ranking/match evidence. Revoked access removes contents from all query projections, including semantic results. A change cursor can retrieve additions, changes and authorized deletion information without reloading the complete corpus; expired cursors require an explicit resynchronization. |
| R-051 | Knowledge work distinguishes sources, conversation notes, working notes, focused insights, reusable knowledge and personal journal entries. Processing state, review/confirmation, freshness and validity remain separate properties. | A user can capture free text, process it from an inbox state and derive a source-linked result without forcing every sentence into a field. Typed relationships can express derived from, supported by, contradicts and supersedes. Completion does not imply verified or current knowledge. The personal journal is distinguishable from the immutable technical change Journal. Any later import requires an explicit mapping of source kinds, states and relationships, including unresolved values. |

External references must retain source identity and attribution. Any cached content, index or context snapshot must have a declared update/deletion policy and enforce current access; source permissions and installation/workspace boundaries cannot be bypassed by a previous retrieval. Ordinary records and external documents remain data. Instructions found inside them do not become authorized policies or skills by being retrieved.

Knowledge records hold useful conclusions, sources and work state. Internal reasoning traces are not a knowledge or execution-storage requirement. Search architecture, indexing technology, source connectors, ranking, context budgets, graph depth and cursor retention remain design decisions.

#### Profiles, delegation and execution

| ID | Requirement | Later acceptance criterion |
| --- | --- | --- |
| R-052 | Agent profiles, rules and reusable skills have identifiable versions, provenance, scope and publication/withdrawal state. Definition editing and authorization for unattended use can require different rights. | A job identifies the approved profile/rule/skill versions actually used. | R-053 | Delegation separates the business Responsible reference, selected agent profile and authenticated authorizing user. Effective authority is bounded by current user rights, approved job scope and the runner's allowed capabilities. | A user delegates a defined result or subtask with explicit allowed actions. The backend derives the acting user from authenticated authorization; an agent cannot select a more privileged identity. Profile changes do not grant credentials or tools. Revocation, reduced user rights or expired authorization stops subsequent unauthorized actions. An unclear or broader action requires a new decision rather than implied permission. |
| R-054 | A concrete agent job is separate from its execution attempts, recurring automation and produced business contents. Jobs preserve goals, source context, questions, decisions and a concise resumption point. | A job can be processed partially, interrupted and resumed by another eligible runner without relying on a private chat transcript. Each attempt records runner/model identification, actual definition versions, start/end, progress, errors and result references. A stale context or conflicting record version is resolved explicitly. Results live in appropriate linked records; an execution log does not become a competing knowledge store. |
| R-055 | Recurring automations specify schedule/time zone, enabled/paused state, job template, execution authorization and a policy for missed occurrences. Existing schedulers can implement the agreed contract without duplicate schedules. | Concurrent scheduling/claim requests create at most one job for a scheduled occurrence. An expired or superseded claim cannot authorize further writes. Recovery inspects uncertain prior action outcomes before retrying, using idempotency/reconciliation where supported. A lease alone is not treated as exactly-once external delivery. Failures and retry limits remain visible, and cancellation defines what can still finish. |
| R-057 | A common work view presents delegated work, waiting questions, attempts, results and changes to authorized people and AI clients, including from a usable mobile interface. | From a business record, users can distinguish queued, running, waiting-for-user, interrupted, failed, cancelled and completed work and navigate to its results and permitted history. A required decision pauses dependent work. Another team member can understand what was done and what remains under their own rights. Journal provenance identifies the authorizing user and agent/execution context without disclosing credentials or internal reasoning traces. |

These concepts do not prescribe seven additional freely editable object types or a particular queue schema. Claims, authorization, scheduling and execution transitions require protected backend operations. Displayed states and descriptive fields alone cannot enforce them. Existing task assignment through Access principals remains unchanged; selecting an agent or granting foreign access does not assign a human participant or notification audience.

Client integration must distinguish discovering/reading a skill, actual host activation and successful execution. A provider-neutral, minimal bootstrap can locate an approved profile, check capabilities and load context; its presence cannot prove that a client supports native skill activation or unrestricted profile switching. Each supported client/runner needs its own acceptance evidence. Credentials remain in the designated secure credential mechanism, separate from profiles, skills and job contents.

#### Sovereignty and operation

| ID | Requirement | Later acceptance criterion |
| --- | --- | --- |
| R-058 | The connected work model remains self-hostable and portable, with documented interfaces and a full-fidelity export/recovery path for user-owned contents, definitions, relationships, files and retained history. #### Later end-to-end acceptance

Before assigning a delivery version, select a first workflow and measurable limits. Candidate acceptance spans an authorized user capturing work from a mobile client, delegating a bounded job, obtaining source-linked context, saving a linked result, interrupting an attempt and resuming it from another eligible runner. Verify competing claims, revoked access, unavailable/stale sources, pending user decisions and uncertain external-action outcomes. The user must be able to inspect the resulting state and continue without reconstructing the original chat. These are later acceptance targets, not completed tests or a selected pilot.
