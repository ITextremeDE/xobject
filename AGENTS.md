# xObject project instructions

## Purpose and sources

xObject is ITextreme's planned metadata-driven, API-first application for connected business data. Version 1 combines Contacts & Relations, Projects & Tasks and user-defined object types. The PRD defines a 22-object target catalog with five V1 objects, 11 additional Contacts objects deferred to the next version and six additional Projects objects deferred beyond V1; `docs/domain-profiles.md` provides draft starter fields/relationships and acceptance cases for all 22, with unresolved domain contracts clearly separated from implemented features. Documents & Communication and the other target modules are later scope.

Read [README.md](README.md) and the [documentation index](docs/README.md) for orientation and [docs/PRD.md](docs/PRD.md) for requirements, acceptance criteria and open design decisions. Preserve requirement IDs when refining the PRD. Do not treat a specification or proposed acceptance scenario as an implemented feature or a passed test.

OpenProject is the source for operational tasks, priorities and dependencies. The repository owns requirements, architecture decisions, code and versioned documentation. Keep private planning details, credentials and internal infrastructure information out of this public repository.

## Current state and commands

The repository contains a local backend technical spike in `apps/server`, with npm workspaces, a lockfile and a GitHub checks workflow. A first React/Vite web client in `apps/web` uses shared contracts in `packages/contracts`. There is no installation package or software release. The experiment supports typed custom fields, shared Type/Status/Category configuration and workspace User/Designer memberships. Content access follows administrative ceilings, graded ownership and foreign access in ADR 0027; complete version-1 delivery remains open.

From the repository root, use `npm ci`, `npm run typecheck`, `npm run build` and `npm test`. Tests require Docker and start an isolated disposable PostgreSQL container. See `docs/development.md` for `npm run db:init`, `npm run admin:create` and `npm run dev`; never point experimental initialization at a production database. No lint command is established.

The independent public project website lives in `apps/site`; it is not an application release. Run `npm ci`, `npm run typecheck`, `npm run build` and `npm test` in that directory. Browser tests require Chromium (`npx playwright install chromium`). See `docs/website.md`.

Website components use the shared ITextreme COS roles, Tailwind CSS 4, Lucide and selectively adopted `@shadcn` `base-nova`/Base UI primitives. Follow the component rules in `docs/website.md`: built-in variants, semantic tokens, native semantics and composition before custom markup. Astro uses `rsc: false`; render static React primitives at build time and add client hydration only for required interactions.

For documentation changes, check Markdown structure, relative links and section anchors, requirement references, whitespace and unintended sensitive content. `git diff --check` is an available whitespace check; include newly created files in review because untracked files are not covered by that command.

## Agreed architecture

- Before the first release, maintain one current installation in `apps/server/src/schema.sql` and its initial module catalog. Do not add development-version migration chains, compatibility APIs, alternate DTO generations or fallback ownership storage. `db:init` accepts only an empty database or an identical current installation; `db:reset` is an explicit disposable-local-database operation. Application startup verifies the schema/catalog fingerprint. Preserve real business history, optimistic versions, validation, permissions and journal atomicity. Whenever an authorized change makes the test schema, fixtures or generated assets stale, rebuild the affected local instance/assets and reapply the current optional demo seed as needed; this standing instruction authorizes disposable test-data replacement. Tests target the current model, not historical development installations. From the first release onward, supported updates must fully migrate data/schema/configuration to the target model before serving it; keep version handling in dedicated upgrade tooling, never in parallel runtime models, legacy DTOs or fallback storage. Initial released updates require stopped application processes/writers, a consistent backup and successful target-schema/integrity checks before restart; a failed update stays stopped until consistent recovery. No rolling mixed-version operation is planned initially. See ADR 0028. Release upgrade/backup/restore tooling remains to be designed and implemented.

- The permission model is PRD section 4 and ADR 0027, extending the historical ADR 0026 ACL. Use the shared finite resolver: direct ownership precedes group ownership and public fallback, any ownership precedes foreign access, and every inherited path is bounded by its weakest membership/foreign edge. Personal blocks foreign access; Confidential requires permission along the complete path; record foreign maxima and administrative object/field ceilings always apply. Create is separate, missing user Create inherits active group grants, and duplication requires both Duplicate and Create without copying unreadable fields. Nested membership cycles are rejected; foreign cycles terminate without grants or escalation. Group membership alone never opens coworkers' records. Only Administrators manage base rights, sensitivity and graded memberships; explicitly delegated owners may manage only foreign rules on their own records within their object ceiling. Full can manage record security within object/field limits, with explicit public confirmation. Preserve current-session revocation, pre-count/search/paging predicates, current-rights history, field restrictions and hidden retained links. Object labels/sensitivity remain one optimistic atomic operation; the protected Access principals field has quick multi-selection plus a tabbed detail draft, applied locally and persisted only by the normal record Save. `update_record.security` and dedicated `configure_record_security` share one writer; combined contents/links/security writes have one source-version increment and change ID. Preserve explicit public confirmation and reset/dirty guards. Record security uses the record version; foreign configuration uses the workspace security version. Calendar-only writes/projections, notification delivery and creation templates remain later scope. No production rights-transfer framework is needed for disposable local test data; use the current installation baseline in ADR 0028; unreleased development schemas are recreated, never upgraded.

- Module naming and shared-object forms follow ADR 0025: Contacts, Projects and Documents are extensible module identities. Store common object form groups, field UUID order and widths in metadata; preserve global validation, required fields, shared values, optimistic versions and atomic definition journals. Supplied Contacts use fixed kind-specific cores under ADR 0025; their designer layouts contain only additional fields and custom relationships. Contact kind is selected before creation and immutable in normal updates; derived name/controller inputs stay out of the contact form. Intended core field input aids remain configurable. The current base module contributions and common forms are implemented; remaining domain templates and released upgrade tooling remain separate. Reserve catalog object technical names against custom creation even with modules disabled/planned; never adopt existing custom objects by name. Keep required fields available in the common object form.

- Primary levels and relationship endpoint conditions follow ADR 0024: fixed module-supplied Contact/Project/Case UUID roles (no role reassignment API/MCP), ordered parents, one stored direct link and shared API/MCP context. Candidate constraints apply before pagination; conditional record edits cannot invalidate retained edges. Object-level Primary requiredness uses retained structural UUID paths, includes recycled records and descendant effects, and shares configure_object_settings/model locks with normal writes; it grants no visibility. Required Primary form elements stay visible. Protect bound objects and single-choice controllers/options, retain optimistic versions and atomic per-property journals. Use the shared applicability editor and UUID-normalizing contracts; never infer domain roles from names.

- Relationship-type configuration follows ADR 0018: protected Primary/General defaults, workspace-scoped endpoint pairs and translated side labels/cardinalities (one left:right cardinality in the UI, separate endpoint required-link settings), common User read / Designer or Administrator write access, optimistic atomic property journals and explicit draft/active rules. The read-only Tree/context projection follows ADR 0020: Projects-gated Primary-only descent (General/custom links stay in the Dossier), paginated lazy branches, bounded context and path-based cycle guards with keyboard navigation. Record header actions and linked creation follow ADR 0019: use list_record_link_options and existing localized side labels; General-only objects are direct items. New records use create_record.linkFrom with source/relationship versions, source Edit plus target creation rights and atomic record/edge journals; preserve source links and enforce cardinalities. Record relationships follow ADR 0019: composite registry/edge identities, atomic versioned record/relationship writes, final-state cardinalities, Primary uniqueness/cycles and one shared journal event projected to both endpoints. Activation and active-rule changes preflight under the existing model lock (R-023). Preserve foreign-key dependencies, symmetry and inactive-language retention. ADR 0021 restricts custom types to one object pair, fixes used pairs/direction and makes General always available. Workspace Projects activation gates globally available Primary association; fixed supplied UUID bindings constrain its parent levels; disable only after removing Primary edges and clearing object-level requiredness. The Modules settings area currently lists the three-entry database-backed prototype catalog; the target catalog and version scope are defined in the PRD. Projects & Tasks activation supplies protected base objects and fixed Primary levels. Structured contact fields support ordered name parts, multiple emails/phones/addresses/websites and birthdays with an optional year, shared whole-field permissions and atomic per-field history. Contacts activation supplies protected Contacts and Distribution lists, fixed Contact kinds, permission-aware derived names, Organization membership, direct Identities and explicit distribution membership. Existing Projects bindings reuse the same Contacts identity. Generic relationship attributes are implemented; the Projects, Cases and Tasks have supplied lean profiles and a shared temporal codec; recurrence, calendar parties and later object templates remain pending; Contacts and Distribution lists are locally accepted; standards exchange and full-product release acceptance remain separate. Documents & Communication remains planned. At most one Organization per Contact person record is enforced by the supplied membership relationship. Identities is a configured symmetric relationship list directly on Contact person/Individual contact records, not a separate object type; it links records of the same person without merging content or permissions and is distinct from user accounts and the technical identity registry.

- Dashboard and table navigation follow ADR 0016: real workspace-scoped metrics/records through shared API/MCP checks, active definitions only, effective-zone daily activity and fixed standard-column projection. Reuse RecordDataTable/TablePagination; selection is current-page and does not authorize bulk writes. Keep remote filters/sorts/pages in URLs and enforce ADR 0027 before counts, filters and pagination. Sidebar search combines permitted navigation and authorized record search.

- Instance administration follows ADR 0015: Administrator-only user provisioning/activation/admin status and global journal reads; mandatory first password change gates every application operation except own security inspection/change. Keep credential/flag/session changes atomic and secret-free. Never hard-delete users/groups or infer an old workspace creation time without its original event.

- Time zones follow ADR 0014: named workspace default and nullable own-user override, atomic versioned localization writes, UTC instants at API/MCP boundaries and date-only semantics. Use the shared effective-zone context for all timestamp display/input. Reject DST gaps and require explicit overlap occurrence; never infer existing workspace zones from the server location. Regional display follows independent workspace settings and nullable personal per-property overrides, with exact numeric strings and date-only semantics. The record date picker uses the effective locale and first weekday; calendar views remain future work.

- Workspace languages follow ADR 0012: installed German/English catalog, nonempty independent interface/label selections, available default, retained unavailable preferences/translation history and common API/MCP checks. Workspace groups follow ADR 0013: Administrators manage memberships/activation, Designers create empty groups/rename, Users read. Journal name/member/state changes atomically; remove direct group memberships when workspace access is removed. Inactive references remain readable/retainable but cannot be newly assigned.

- Shared workspace appearance follows ADR 0011: use the pinned shadcn palettes/fonts, validated typed tokens, per-property atomic journals and optimistic versions. Only Administrators and the workspace's Designers may change it. Personal light/dark/system mode stays browser-local. Preserve font licenses, local serving, preview/draft guards and cleanup across workspaces/sign-out.

- Personal account security follows ADR 0010: shared owner-scoped API/MCP operations, transport-derived current-session identity, Better Auth password crypto, atomic secret-free journals and no alternate auth-management route bypass. Never expose credentials or session bearer tokens in session lists or journals. Workspace roles do not broaden account ownership.

- Record recycling/restoration follows ADR 0029: store lifecycle metadata on the existing registry identity; enforce Delete for recycle and Full for restore, optimistic record versions and atomic lifecycle journals. Normal policy predicates/selectors exclude recycled rows, including for Administrators. Retain contents/policies/edges/history and cardinality slots; unavailable endpoints disclose no content. Validate current fields and retained links on restore without silently dropping data. Confirmed permanent deletion retains immutable history for installation Administrators and projects only content-free deletion notices to other authorized users under R-040. Keep tombstone policy and frozen field/event/context eligibility separate from live contents; require both current rights and prior visibility, remove operational edges/rows atomically, preflight surviving dependencies and never rewrite stored journal values.

- Definition lifecycle follows ADR 0009: usage includes current and historical values (including zero/false); used definitions are deactivated, and unused ones may be deleted only with confirmation and dependency checks. Preserve tombstone identities and journals, couple Type/Status fields, use RESTRICT without cascading other data, and preflight reactivation. Inactive fields accept no record writes; inactive object types allow read-only content access under existing permissions.
- Field descriptions/hints, typed omission-only creation defaults, supported scalar uniqueness and immutable business numbers follow ADR 0030. Keep input rules separate from type configuration, honor current field creation rights and complete controller values, retain unique/numbered slots through recycling and validate metadata changes atomically. Number allocations/counters/journals share the record transaction; numbering uses workspace-zone periods and exact integers, never manual values or preview reservations.
- Custom field types, PostgreSQL mapping, precision, reference scope and safe conversions follow ADR 0007. One shared field editor serves creation and editing; do not build separate forms.
- Workspace roles follow ADR 0008: Administrators are installation-wide, Designers configure their assigned workspaces, and Users view workspace settings/definitions read-only. Only Administrators manage memberships. Memberships do not grant business-content rights; apply object/field/record permissions under ADR 0027. Resolve all access from the current database inside the common API/MCP transaction.
- The installation-wide Administrator role is the server-owned `sys_users.is_admin` flag (default false). Resolve authorization from the current database value, not user input or cached profile/session data. Normal signup/profile updates must not write the flag.
- Every business field exposes a required flag. Text flags live in `sys_fields.required`; shared choice flags remain in classification configuration. New objects have no optional standard fields. Keyword, the Type/Status pair and Category can be installed through Add field; installed fields default to optional. The shared editors may stage requiredness or versioned classification rules before atomic installation through `add_standard_field`. Preserve existing field definitions and required flags. Enabling stricter flags must preflight existing data; all API/MCP record writes validate the resulting record.
- Shared Type/Status/Category rules and stable option identities are defined in ADR 0006. All three fields have independently configurable required flags; Without Type has its own Status options. Validate stricter configuration against existing records and preserve retained inactive values. Unused Type/Status options may be deleted only if no current or historical record references remain; retained Status options must keep a valid Type. Journal deletions atomically and never reuse deleted option identities.
- PostgreSQL is authoritative for definitions, records, relationships and journal data. Object types use their own data tables; current collection/reference storage follows ADR 0007. Specify additional storage models and future released migrations before implementing them.
- Use readable workspace-prefixed data table names (`itx_contacts`) and the reserved `sys_` prefix for system tables, as specified in PRD section 3.1 and ADR 0001. Keep UUID identities separate from technical names and editable display labels. Workspace codes and technical names are fixed after creation in version 1; prefixes do not enforce authorization.
- Database integrity, definition draft versions, scoped schema/workspace locks, targeted record-graph checks, the current installation baseline and separate operator/runtime database roles follow ADR 0022. For future released upgrades, never edit already shipped numbered migrations to implement a new change; never auto-retry a stale metadata draft with a refreshed version. Runtime DDL remains necessary for dynamic business tables; keep system-table ownership and journal/ledger mutation rights with the operator.
- The backend experiment evaluates Fastify, Kysely/pg, Better Auth and the official MCP SDK; see ADR 0002 for scope and outstanding production decisions.
- Custom fields cannot use the reserved standard field names or their German/English labels; enforce this through every API/MCP creation and rename path, even if the standard field is absent. Definition-label forms use one shared `TranslatedLabelInput` with a language selector, per-language translation status and a retained multilingual draft. Save all translations together; require at least one label. Do not add a separate input for every language.
- Definition labels use JSONB language maps, separate from stable technical names. Follow PRD section 3.3 and ADR 0003 for user/workspace language fallback and physical column order. Preserve existing records and historical journal values during migration; do not automatically rebuild tables solely for ordering. An explicitly authorized development-data rebuild is a separate maintenance operation.
- Backend, API and MCP use TypeScript on Node.js in a modular monolith. Web uses React, TypeScript and Vite.
- UI uses Tailwind CSS and shadcn/ui with Base UI (`base-nova`), Neutral and Lucide. The application shell follows official `sidebar-07`; record lists reference the Tasks example. Prefer standard components, existing variants and composition, with minimal custom CSS and centralized semantic tokens/CSS variables.
- Record Journal and conditional field applicability follow ADR 0023: retain event/edge identities, reconstruct historical kind/configuration, page/filter on the server and evaluate complete final records through API/MCP. Protect controller dependencies and never silently clear inapplicable values. Generic rules do not infer Contacts ownership from names.
- Record creation/editing uses dedicated pages under ADR 0017, one shared form, grouped fields, retained tab drafts and formatted record history. Keep form field order separate from alphabetical definition administration and physical storage. The local fictional demo seed creates actual relationships through shared application operations and never resets existing data. Keep private seed manifests and database recovery artifacts outside Git.
- React Router owns web navigation and list URL state; preserve direct-link refresh, guarded Back/Forward, workspace scoping and API/asset error responses when adding routes. See ADR 0004 and the development guide.
- Settings follow the official shadcn Sidebar 13 dialog pattern. The Personal group contains Profile, Account & security, Appearance and Language & region; these edit own-account preferences, browser theme, language, time zone and regional overrides. Administrator-only Instance settings contain Users and the global Journal. The Workspace group contains Modules (catalog, activation and fixed Primary explanation), General (editable name, immutable code), Language & region (language policy, time zone and regional display defaults), and Object types (alphabetical standard shadcn Select, editable translated labels, read-only technical names, a field-definition table with integrated field input aids, a shared side-by-side Type/Status editor and a Category editor). Keep `/settings` directly accessible and preserve Save/Reset, keyboard access and unsaved-change protection.
- Configuration choice values use the shared compact ChoiceValueEditor for classification and custom fields. Type/Status configuration shows the selected Type beside its statuses. Keep translations, identity, sorting, defaults and lifecycle rules shared; expanding a row does not save it. Form designer actions use the enclosing DialogActions footer with native form association. Definition history reuses RecordJournalTable; journal context names supplement rather than rewrite historical snapshots.
- Dialog actions use the shared DialogActions footer: Cancel left and Create right for creation, Close left and neutral Reset then primary Save right for editing; read-only dialogs offer dismissal only. Disable unchanged/invalid submissions, allow resetting invalid drafts, and guard all close paths during pending operations. Confirmations place Cancel left and the destructive decision right.
- Normal dialogs expose the standard localized top-right close button; keep header space clear and preserve pending/unsaved-change guards. Footer close actions may remain. AlertDialog confirmations use explicit decision actions without an X.
- Loading states reuse standard Skeletons and follow the actual route/region. Keep known headings and record-table headers, control slots and page size stable; do not show empty results or fake counts/pages while pending. Lazy settings/classification fallback dialogs share their loaded frame; unknown session state uses a neutral progress indicator. Preserve existing content during background refresh.
- Keyboard actions are centralized in `apps/web/src/lib/keyboard.ts`, exposed through localized help and standard Kbd hints. Preserve native Base UI keyboard navigation, visible focus, focus return, browser shortcuts, input/IME handling and pending/validation guards.
- UI, API and MCP use the same backend rules. Do not implement a capability exclusively in the UI or rely on UI checks for correctness or authorization.
- Git stores application source and project documentation, not live business records. Self-hosting must not require a Git account or a user-owned repository.
- Official self-hosting targets prebuilt images and Docker Compose on Linux. Concrete frameworks, versions, security mechanisms and operational commands remain design decisions until specified.

The intended monorepo layout is `apps/web`, `apps/server`, `packages/contracts`, `deploy` and `docs`. Only create the parts required by the active task; this list is not an instruction to scaffold the application.

- Form groups have no domain meaning. New custom objects start with an editable General proposal; new elements remain Unassigned until placed, and deleting groups unassigns elements without deleting data. Module layout proposals remain editable independently of protected field structures.

- Keep other supplied domain templates lean under PRD section 6.3: essential fields/relationships, configurable input aids and editable forms, with extensions by Designers/Administrators. Preserve confirmed rules, module protection and role boundaries; do not add speculative specialist workflows.

- The staged structured-domain architecture is ADR 0032: one finite typed `structured` codec registry, JSONB in existing object tables, relationship-owned fields/values, shared UUID identities, whole-field rights, both-endpoint attribute authorization, immutable per-field journals and sparse versioned occurrence overrides. Nine contact codecs, the shared temporal codec and `list_field_schemas` are implemented. Relationship-owned fields and both-endpoint permissions/history are implemented. Structured Contact references, calendar-party codecs and occurrence operations remain planned; do not present them as existing capabilities.

- Standards-aligned Contacts, Distribution lists, Appointments, Vacations and Tasks follow PRD section 6.4 and ADR 0031. Specify explicit vendor-neutral vCard/iCalendar mappings and round-trip criteria; keep exchange identities and domain time-zone/recurrence semantics distinct from display settings. CardDAV/CalDAV and JSON exchange are not implemented by this decision. Peer-specific limitations never redefine objects/categories or grant content rights.

## Product invariants

Consult the PRD for complete behavior. In particular:

- Workspaces isolate contents, definitions, groups, module activations and number sequences for regular users. Administrators have installation-wide content access. Keep the explicit Administrator exception distinct from object-level Full access.
- Agents act with their user's effective rights. All access channels must apply the same authorization, validation, feature entitlements and journal rules.
- Contact kind is separate from Type. Each Contact is exactly one of Organization, Individual contact or Contact person. Do not merge these concepts or reintroduce simultaneous contact kinds.
- A shared object type can belong to multiple modules without duplicating records or shared values. Protect supplied definitions while allowing the agreed configuration of input aids and user-defined extensions.
- Each record has at most one direct Primary association. Derive ancestor context from relationships; do not independently store competing context values or infer permissions from the hierarchy.
- Record one journal entry per field change, group related entries by change ID, and persist changes and their journal atomically. Apply historical-value permissions and the specified permanent-deletion behavior.
- Deactivate data-bearing user-defined fields instead of deleting them. Reject unsafe field conversions. Activate stricter relationship rules only after existing affected data satisfies them.

Uploads, attachments, import/export, SSO, native clients, offline synchronization, Kanban and calendar views are outside version 1. Do not add them to the initial scope implicitly. General undo and computed fields are also outside the current delivery baseline.

## Working approach

1. Inspect branch, worktree, relevant instructions and the affected PRD requirements before editing.
2. Preserve unrelated and user-owned work. Make the smallest coherent change for the authorized objective.
3. Resolve the relevant open design decisions before implementing the affected behavior. Record significant decisions as ADRs under `docs/adr/` when that work is in scope.
4. Implement in small, end-to-end slices. Use feature branches, pull requests and review for implementation work in line with the agreed workflow.
5. Validate the affected acceptance criteria with appropriate checks. Run builds when application code or dependencies change; do not run nonexistent or unrelated application builds for documentation-only edits.
6. Report what changed, what was actually verified, and remaining uncertainties. Keep implementation, acceptance, deployment and publication distinct.

## Commits, remotes and publication

Follow the active user's authorization for commits, pushes and publication. Stage only reviewed files or hunks, inspect the staged diff, and exclude unrelated changes and secrets. Use Conventional Commit messages in English.

GitHub `origin` is the leading public remote. `forgejo` is the second private remote. When publishing is authorized:

1. Push the intended branches/tags to `origin`.
2. Push the same intended state separately to `forgejo`.
3. Verify both remote references independently and report any partial failure.

Do not substitute an automatic pull mirror or develop divergent histories on the two remotes. Git pushes do not back up issues, reviews, PR discussions or release attachments. Do not force-push, rewrite history, alter protections or deploy unless those actions are covered by the user's authorization.

- Relationship attributes use the same field UUID namespace and typed writer: exactly one object/relationship owner, edge-local UUID-keyed JSONB values, edge/definition/source versions, both-endpoint field rights, and immutable per-field events shared by both endpoints. Contact-person and Individual Job title/Department/Function are direct Contact fields in Professional details beneath Photo; they remain unchanged on Organization reassignment. The supplied Organization membership has no attributes. Generic relationship attributes remain separate and are not copied to a new edge automatically.
- Module contributions bind shared object/field identities and template versions. Additive updates preserve authored forms/input aids; structural collisions fail atomically. Deactivation retains data/views and keeps shared objects active when another contributor remains enabled. Each object has one common `default` form with all applicable fields; UI/API/MCP have no module context selection. Released upgrade tooling remains separate.

- Activity work assignment and ownership use the one protected Access principals list. Supplied Tasks have no separate assignment field or assignee storage. Responsible is a coordinating reference; foreign access grants rights without adding participants. Projects/Cases/Tasks remain sensitive and use editable paired Details/Schedule starter groups.

- Configurable sidebar navigation follows ADR 0033: module sections ordered by catalog priority, per-module entry identities for shared objects, protected UUID-bound Contact-kind lists, independent versioned workspace/personal layouts and an initially visible optional Resources block. Use standard Sidebar 02/07/08 composition and the shared command dialog. Navigation visibility never changes content rights; Contact-kind filtering must apply current field/record predicates before counts/paging. Preserve unavailable layout identities, atomic per-property journals, keyboard alternatives to dragging and inherited-layout restoration.

- External API/MCP access follows ADR 0034: user-owned opaque hashed tokens, interactive/password-confirmed issuance, one-time secrets, transport/read-only limits and expiry/revocation checked inside each application transaction. Password changes/deactivation revoke tokens. Token management requires an interactive session; bearer tokens cannot proliferate credentials. Preserve actor/channel/credential/agent provenance, secret-free logs and portable generated OpenAPI input/output schemas. Run `npm run api:generate` after contract edits; `api:check` detects drift. API versioning is independent of the application release.
